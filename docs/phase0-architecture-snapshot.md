# Phase 0 — Architecture Snapshot

This document records the architectural baseline before changes to the food-intelligence production path. It is a qualitative snapshot; the deterministic inventory generated by `scripts/phase0_audit.py` provides the machine-readable counts.

## Existing repository surfaces

The repository currently includes Python modules for ingestion, corpus handling, representations, graph construction, retrieval, compatibility, novelty, constraints, pipeline orchestration, evaluation, synthetic benchmarks, and storage. A PostgreSQL schema and a Python test suite are also present.

The current implementation is a research prototype. The presence of a module or relationship type does not establish that its capability is integrated end to end or scientifically validated.

## Known architectural risks

1. **Competing paths:** newer intelligence/retrieval components coexist with older fixture/MVP components.
2. **Fixture coupling:** parts of storage and ingestion depend on `FoodMVP` or fixture-oriented parsing.
3. **No admitted real corpus:** data acquisition and rights review remain blockers for scientific claims based on real recipe data.
4. **Metadata-only adapters:** some source adapters describe candidate sources but do not provide authorized ingestion.
5. **Scoring is not dynamics:** ingredient compatibility scores do not simulate physical or chemical transformations.
6. **Graph is not a simulator:** typed edges can represent transformations but do not execute their governing dynamics.
7. **Synthetic evaluation limits:** synthetic benchmarks are useful for regression and plumbing, not evidence of real-world predictive performance.
8. **Sensory evidence limits:** inferred or synthetic taste/odor signals must not be presented as measured sensory outcomes.
9. **Scientific provenance:** data, model, source, condition, and license provenance must follow observations through the full pipeline.

## Required architectural direction

The target architecture is organized around a reproducible experiment lifecycle:

`Canonical World State → Intervention → Dynamics → Experiment Execution → Observation → Experimental Memory → Evaluation/Learning → Next Experiment`

A multi-view knowledge graph, scientific databases, and predictive models support that lifecycle. They do not replace it.

## Non-goals for Phase 0

Phase 0 must not introduce a new simulator, alter compatibility scoring, train a model, ingest unlicensed data, remove legacy production code, or claim scientific discovery. It establishes the inventory, tests, CI gate, architectural snapshot, reproducibility rules, and entry criteria for subsequent work.

## Exit gate

Phase 0 is ready to close when:

- the repository inventory is deterministic and machine-readable;
- static syntax and required-path checks pass;
- existing tests and CLI smoke tests pass across the supported Python matrix;
- known architecture debt and scientific limitations are documented;
- synthetic-vs-measured evidence boundaries are explicit;
- the next phase has a bounded scope and testable acceptance criteria.
